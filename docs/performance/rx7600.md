# RX 7600 (gfx1102) performance work on ROCm 10.1.0

This fork (branch `perf/benchmark-gates`, based on TheRock `therock-10.1`, commit `b324869`) adds tooling and measured
configuration for making **inference on one Radeon RX 7600 (gfx1102, RDNA3, 8 GB)** faster than stock ROCm 10.1.0.

**Scope.** RX 7600 only. CDNA / Instinct parts (including older ones such as MI50/gfx906) and multi-GPU are out of scope and untested.
Nothing here is claimed for other GPUs.

**Honesty note.** The fork changes **no ROCm library or compiler code**. The speedups come from (a) enabling stock PyTorch
kernels that ship disabled for this GPU, (b) a weight layout and decode strategy that suit this GPU better, and (c) measurement
tooling that stops us fooling ourselves. See [Corrections made along the way](#corrections-made-along-the-way).

## Results at a glance

Tested on: Radeon RX 7600 (gfx1102), Xeon E5-2680 v4 host, Ubuntu 26.04, ROCm Core SDK 10.1.0 + torch 2.14.0+rocm10.1.0 installed from
`stable.repo.amd.com` into a venv (no root), transformers 5.22.1.

| Workload | Stock | Fork | Speedup | Evidence strength |
|---|---|---|---|---|
| 0.5B synthetic decoder, prefill 2048 tok | 312.8 ms | ~86 ms | **3.65x** [3.640, 3.658] | paired, 10 pairs, 95% CI, correctness-gated |
| 0.5B synthetic decoder, decode/token | 11.9 ms | ~6.4 ms | **1.88x** [1.873, 1.878] | paired, 10 pairs, 95% CI, correctness-gated |
| TinyLlama-1.1B prefill 1800 tok | 818 ms | 195 ms | 4.2x | single session |
| TinyLlama-1.1B decode/token (HF eager) | 31.7 ms | 22.7 ms | 1.40x | single session |
| TinyLlama-1.1B decode/token (`GraphedDecoder` + fusion) | 31.7 ms | 9.97 ms | 3.2x | single session, tokens identical to HF generate |
| Qwen2.5-0.5B prefill (fp16 / bf16) | 399 / 402 ms | 103 / 110 ms | 3.86x / 3.66x | single session |
| Qwen2.5-0.5B decode/token (`GraphedDecoder` + fusion) | 37.3 ms | 5.98 ms | 6.2x | single session, tokens identical to HF generate |
| 4-layer d512 training step (attention only) | 90.6 ms | 50.3 ms | 1.8x | single run; loss curve matches |

"Fork" = `rocm_perf_profile` + `fast_linear` (+ `GraphedDecoder` where stated). Small-M GEMM tuning (TunableOp) adds ~1.1x on
cold-weight decode shapes and 1.09x on 2048^3; it is not part of the default stack.

Model quality is unchanged within fp16/bf16 noise: perplexity over 16k tokens differs by < 1e-4 relative (TinyLlama 4.57627 vs 4.57635;
Qwen fp16 7.03619 vs 7.03653).

## Quick start

```bash
# 1. environment (no root; needs uv). Creates ~/rocm-env with ROCm 10.1.0 + torch for gfx1102.
build_tools/perf_tools/setup_rx7600_env.sh
. ~/rocm-env/.venv/bin/activate

# 2. see what the runtime profile would change (detects the GPU via rocminfo, never imports torch)
python build_tools/perf_tools/rocm_perf_profile.py --dry-run

# 3. run anything with fused attention enabled
python build_tools/perf_tools/rocm_perf_profile.py -- python your_script.py
#    (or call rocm_perf_profile.apply() before `import torch`; ROCM_PERF_PROFILE=0 disables it)
```

Inference code:

```python
import torch
from transformers import AutoModelForCausalLM
from fast_linear import convert, fuse_projections   # build_tools/perf_tools
from fast_tune import tune_decode, load_tuning
from fast_decode import GraphedDecoder

model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float16, attn_implementation="sdpa").cuda().eval()
convert(model)                                              # inference-only weight layout, state_dict stays standard
fuse_projections(model)                                     # optional, +1.1x decode (needs convert first)
# batched serving only (B >= 2): tune_decode(model, (2, 4, 8), 'tune.csv') once, then load_tuning('tune.csv')
dec = GraphedDecoder(model, max_len=2048, max_batch=4, compile=True)   # first call compiles (~40 s)
tokens = dec.generate(input_ids, max_new_tokens=128, attention_mask=mask)   # [B, new]; greedy; left-padded prompts
```

Unit tests: 34 in total (12 paired gate, 6 status guard, 6 profile, 10 fast_linear). Run `python -m unittest build_tools.tests.perf_tools_test build_tools.tests.benchmark_status_test build_tools.tests.rocm_perf_profile_test build_tools.tests.fast_linear_test`; the 10 `fast_linear` tests skip when torch is not installed. No GPU is needed for any of them. The GPU-dependent checks are the scripts under `examples/gfx1102/`.
(`fast_linear_test` needs torch and is skipped without it).

### How the pieces relate

```
 rocm_perf_profile  -> fused attention (prefill 3.0x, decode 1.45x on the 0.5B model, 8-23x on the attention op itself)
 fast_linear        -> [in,out] weights (+1.20x prefill, +1.29x decode on top)
 fast_decode        -> static cache + compile + graph (decode 22.7 -> 11.0 ms/token on TinyLlama)
 paired_benchmark   -> how every claim above was measured (and the A/A calibration behind its thresholds)
```

## Detailed results

### Attention (fused AOTriton vs stock math fallback)
Stock PyTorch 2.14 gates fused SDPA on gfx1101/1102/1150/1151/1200 behind `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL`; without it SDPA uses the math kernel.

| Case | Flag off | Flag on | Speedup |
|---|---|---|---|
| causal prefill, 32 heads, d128, 2048 tok | 56.8 ms | 2.44 ms | 23x |
| decode, batch 8, KV 8192 | 37.0 ms | 3.86 ms (~278 GB/s, near roofline) | 9.6x |
| decode, batch 1, KV 32768 | 19.0 ms | 2.25 ms | 8.5x |

Correctness (forward and dQ/dK/dV vs fp64, 10 configs: MHA, odd length, GQA 4:1, MQA, bool/float masks, head dim 80, bf16, q!=kv):
errors <= ~1e-3 fp16 / 4e-3 bf16, within 1-3x the unfused fp16 error, all finite. Dispatcher falls back correctly for combinations one fused
backend lacks (dropout, fully-masked rows, length 1 also checked). Files: `e2e/attn_matrix.py`, `e2e/attn_dispatch.py`.

### GEMM
- Compute-bound shapes: tuned (TunableOp) 2048^3 is 1.086x [1.079, 1.092]; 4096^3 1.019x (below the 3% gate).
- Small-M, cold weights (rotating 8 x 33 MB so the Infinity Cache cannot hide DRAM): default rocBLAS/Tensile picks a 128x128 tile for M=16 (0.143 ms,
  ~235 GB/s, ~80% of ~288 GB/s peak); hipBLASLt 64x16 tile 0.128 ms. Only ~1.1x. (The warm-cache 1.83x figure was an artifact; see corrections.)
- `TORCH_BLAS_PREFER_HIPBLASLT` 0/1: no measurable difference on this card.
- A custom Triton GEMV matched plain `x @ w` (both ~265-275 GB/s): the real loss was the weight layout, which `fast_linear` fixes.

### Weight layout (`fast_linear`)
M=1 GEMV bandwidth, `F.linear` -> pre-transposed: K2048/N6144 111 -> 250 GB/s (2.24x); N8192 167 -> 255 (1.53x); K8192/N2048 203 -> 262 (1.29x);
head N32000 182 -> 275 (1.51x). End to end, on top of fused attention: prefill 1.200x [1.198, 1.203], decode 1.289x [1.288, 1.290].

### Decode machinery (`fast_decode`)
TinyLlama, 512-token prompt, 128 new tokens, all with fork profile + fast_linear: eager HF 22.7 ms -> static graphed 13.9 ms -> compiled + graphed 11.0 ms.
Weight-read floor is ~7.6 ms. A synthetic estimate says fusing q/k/v and gate/up GEMVs would save ~1 ms more; not shipped. The remaining time is mostly
unfused elementwise/norm/rotary work that `torch.compile` already partially fuses.

### Other measured behavior (single GPU)
| Topic | Result |
|---|---|
| Launch vs graph, chains of tiny kernels | graph replay 3.2-3.5x faster; capture pays back in 2-5 replays; 10x 4096^3 GEMM only 1.08x |
| Caching allocator | ~3 us alloc/free at 1-256 MB; calling `empty_cache()` every step costs 123-131 us (1-16 MB) to 3.8 ms (256 MB) |
| Copy/compute overlap | pinned memory + side stream hides a 40 ms copy behind compute (efficiency 0.999); pageable gets 0.14. H2D ~6.3 GB/s either way (host-limited, unverified) |
| First-call cost | new matmul shape: median 0.8 ms, max 176 ms (steady 0.23 ms); first conv in a fresh process 2.5 s |
| Process startup | import torch 1.64 s, context init 0.31 s, first matmul 0.15 s; disabling the COMGR cache doubles context init (0.31 -> 0.67 s) |
| Training smoke | 4-layer d512, 60 steps AdamW fp16: loss 4.8680 vs 4.8689; step 90.6 -> 50.3 ms with fused attention; `fast_linear` makes it ~10% slower, so use it for inference only |

### Batched decode and tuning (added)
TinyLlama / Qwen2.5-0.5B, tokens per second, stock HF `generate` (fused attention on) vs fork with fusion (+ tuning at B >= 2):
B=1: 43 -> 100 / 37 -> 167; B=2: 72 -> 173 / 66 -> 284; B=4: 144 -> 302 / 130 -> 463; B=8: 288 -> 430 / 258 -> 796.

## Methodology and lessons

- **Paired runs, A/A first.** Baseline and candidate alternate in randomized order; 95% bootstrap CIs; correctness commands gate every pair. With 200 iterations an identical
  command showed a false 1.08x "gain"; with >= 3000 iterations / 16 pairs the A/A noise is about +-0.5%. Use long runs for launch-bound shapes.
- **State whether weights are cache-resident.** The RX 7600 has a 32 MB Infinity Cache; repeated GEMMs on one 33 MB weight look 1.8x faster than they are.
  Rotate several weight copies for decode benchmarks (`cold.py`).
- **Compare against the real reference.** Token-equality checks must compare against `model.generate` with `min_new_tokens` unset and `repetition_penalty=1.0`
  (Qwen's default is 1.05), not against another variant of your own code.
- **Reset static caches between prompts.** HF `StaticCache` keeps per-layer position counters; reuse without `cache.reset()` silently produces wrong tokens.

## Known issues and open problems

1. `torch.compile(mode="reduce-overhead")` combined with HF `cache_implementation="static"` segfaults on this stack (also on stock; `e2e/hf_graph.py`, `MODE=compile`).
   `GraphedDecoder` avoids it by compiling in default mode and capturing the graph manually. Not root-caused or reported.
2. An earlier script hit `HSA_STATUS_ERROR_EXCEPTION` (code 0x1016) when running an eager prefill after graph capture. A minimal repro did not trigger it and `GraphedDecoder`
   (with `cache.reset()`) does not, so it was most likely a script bug. Unproven; kept at `e2e/hf_cg.py`/`repro_a.py` for reference.
3. HF `StaticCache` without compile ran at ~310 ms/token (unusable); `GraphedDecoder` is the supported path.
   **hipBLASLt handle creation during graph capture (reproducible, no HF needed, `e2e/lt_capture.py`):** a TunableOp-selected hipBLASLt GEMM that was warmed up on one stream and then captured
   with the default `torch.cuda.graph(g)` fails with `Hip error: 'operation not permitted when stream is capturing'` at `hipblaslt.cpp:169` (a `hipMalloc` in handle creation) and then
   the process HANGS instead of exiting. Handles are per stream and capture uses a fresh stream. Workaround: warm up and capture on the same stream. Not yet reported upstream.
3b. Enabling TunableOp makes B=1 decode ~3% slower even with no B=1 entries tuned; not investigated.
4. `fast_linear` replaces tied embeddings/heads with a transposed copy: +136M parameters of memory on Qwen2.5-0.5B.
5. Fused attention kernels are labelled experimental by PyTorch. Validation is limited to gfx1102 and the cases listed above.
6. H2D bandwidth (~6.3 GB/s on a PCIe 4.0 x8 link) was not investigated; the Broadwell host is the likely limit.

## Corrections made along the way

Recorded so nobody repeats the mistakes:

1. A 1.83x skinny-GEMM gain was a cache artifact (cache-warm weights); cold-weight gain is ~1.1x.
2. Early "tokens identical" claims for graphed decode only compared graphed variants to each other. Real comparison against HF `generate` is in `fast_decode` checks.
3. Reusing a StaticCache across prompts without reset gave wrong tokens (2-15% agreement) until `cache.reset()` was added.
4. The runtime profile originally enabled the flag for all `gfx11*`. PyTorch gates only gfx1101/1102/1150/1151/1200 (gfx1100 is already on), so it now targets gfx1102 only.
5. A reference with `min_new_tokens` or Qwen's default `repetition_penalty` silently changes tokens.
6. The suspected stack bug (hardware exception after graph capture) was downgraded to "unproven".

## Not done / out of scope

- CDNA/Instinct (including MI50/gfx906) and any GPU other than the RX 7600; multi-GPU/RCCL (E09); compiler work (E08).
- Sampling, other model families, batch sizes above 8, long-context (> 8k) numerics, multi-epoch training convergence.
- Wiring the paired gate into TheRock CI; upstream pull requests and the PyTorch issue (draft only); any change to rocBLAS/hipBLASLt/LLVM.
- Remaining B=1 decode headroom to the weight-read floor (TinyLlama 9.97 vs ~7.6 ms; Qwen 5.98 vs ~3.9 ms): attention latency, ~1 ms of kernel gaps, GEMV at ~217 vs ~253 GB/s.
